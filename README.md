# PA-Shift タイムテーブル・シフト生成ツール

## 🎯 概要

ライブイベントの PA（音響スタッフ）シフトを自動生成するツールです。バンドのリハーサル・本番スケジュールとメンバーのスキル・条件を入力すると、最適なシフト配置を自動計算します。

## 🆕 主な改善点（v12）

### フロントエンド（templates/index.html）

- **NG時間帯に「終日」スイッチを追加**: メンバー登録画面のNG時間帯（日別）に、「🚫 終日不可（この日は丸一日NG）」というチェックボックスを追加しました。1日中どうしても入れない日がある場合、これまでは開始・終了時刻をダイヤルで `00:00`〜`23:59` に手動で合わせる必要がありましたが、チェックを入れるだけでその日のNG時間帯が自動的に `00:00-23:59` の1件に置き換わるようにしました（`toggleAllDayNg()`）。チェックを外すとその日のNG時間帯はクリアされ、個別の時間帯指定に戻せます。すでに `00:00-23:59` が1件だけ登録されている日は、編集画面を開いた時点で自動的にチェック済み表示になります（`isAllDayNg()`）。あわせて、メンバー一覧のNG時間表示でも `00:00-23:59` は「終日」という文言で分かりやすく表示するようにしました。
- データ形式（`ng_times` の `"HH:MM-HH:MM"` 文字列）自体は変更していないため、バックエンド（`app.py`）や既存の入力JSONとの互換性に影響はありません。

## 主な改善点（v11）

### バックエンド（app.py）

- **初心者（アシスタント）がステージにほぼ配置されない偏りを修正**: 卓は「リーダー確保後の残り枠をアシスタント専用で予約する」仕組みのおかげで初心者も確実に入れますが、ステージには同様の予約がなく、実際には次の2つの要因でステージの残り枠がほぼ常に別のリーダー候補に取られてしまい、初心者はほとんどステージに配置されない状態になっていました。
  1. ステージの優先度計算に `+m["skill_stage"]`（スキル値をそのまま加点）が入っており、スキル3以上の人が常にスキル1〜2の人より2〜4点有利になっていた。→ この加点を削除し、ステージの残り枠は「スキルを問わず」文字通り同列に競わせるようにしました。リーダーの成立条件（最低1名は必須）自体は変えていません。
  2. 卓・ステージどちらの優先度も「卓+ステージ合計の配置回数（`count`）」に応じて一律に下げていたため、卓のアシスタント予約枠で頻繁に卓へ配置される初心者ほど合計回数が早く積み上がり、その結果ステージの優先度まで一緒に下がってしまい、役割バランス補正（`ROLE_BALANCE_WEIGHT`）で押し上げても相殺されて、いつまで経ってもステージに回れなくなっていた。→ 卓の優先度は卓回数（`desk_count`）、ステージの優先度はステージ回数（`stage_count`）だけを見て下げるように変更し、役割バランス補正と矛盾しないようにしました。
  
  この2点の修正により、`registered_bands_7.json`（登録15人中スキル3未満2人・18バンド）で検証したところ、初心者のステージ配置回数が平均1回未満から4〜5回程度まで改善しました（卓中心ながらステージにも継続的に配置されるようになります）。

## 主な改善点（v10）

### バックエンド（app.py）

- **ペース基準値を「登録人数全体の平均」から「ロール・階層ごとの実際の人数」に変更**: v9で導入したペース管理は、`shift_limit`（全バンド数×4÷**メンバー数全員**）という1つの値を全員に適用していました。しかし卓のアシスタント枠は「スキル3未満」の人しか埋められないため、たとえば登録15人中スキル3未満が2人しかいない場合、その2人にとっての実質的な必要回数（合計18枠÷2人＝1人あたり9回）は、全員平均（15人で割った値）よりずっと大きくなります。全員平均を基準にしてしまうと、この2人は実際にはまだ全然回数を稼げていないのに「もう十分働いた」と誤判定され、早期にハード除外されて中盤・後半に出番が回らなくなる、という問題がありました。そこで `_compute_role_pace_baselines()` を新設し、卓/ステージ × リーダー/アシスタントの**実際の登録人数**とバンド数から、階層ごとに適切な「1人あたりの目安回数」を算出してペース判定に使うようにしました。
- **ペースの許容幅を「割合ベース」に変更**: 許容できる前倒し幅（ソフト/ハード超過のしきい値）を固定回数ではなく、基準値に対する割合（`PACE_SOFT_OVERAGE_RATIO` / `PACE_HARD_OVERAGE_RATIO`、下限として `PACE_SOFT_OVERAGE_MIN` / `PACE_HARD_OVERAGE_MIN`）で決めるようにしました。固定回数のままだと、`desk_limit_per_member` などで小さい上限（例: 5回）を明示指定した場合に、その大部分を前半だけで使い切ってしまう問題があったためです（詳細は次項）。
- **`desk_limit_per_member` / `stage_limit_per_member` / `total_limit_per_member` もペース管理の対象に**: これまでこれらの明示的な上限は「達したら完全除外」という総量ベースの制約でしかなく、進行度を考慮していませんでした。そのため、例えば「全員5回まで」と設定すると、少人数のアシスタントがイベント序盤〜中盤だけで5回を使い切ってしまい、後半にはまったく出てこなくなる、という新たな偏りの原因になっていました。今回、これらの明示的な上限が設定されている場合は、その値自体を「ペースの基準値」としても使うようにし（`_pace_target()`）、上限に向かって進みすぎないよう進行度に応じて配分されるようになりました。ユーザーが明示的に設定した上限に対しては、リーダー・アシスタントの区別なくペースのハード除外を適用します（自動推定の基準値に対しては、従来通りリーダーには適用しません）。
- **推奨上限値の推定API（`/api/estimate-limits`）を追加**: 登録済みのバンド・メンバー構成から、卓/ステージ × リーダー/アシスタントごとの「1人あたり目安配置回数」と、詳細設定の上限欄に使えるおすすめのデフォルト値を計算して返す軽量エンドポイントを追加しました。シフトは生成せず、見積もりのみを行います。

### フロントエンド（templates/index.html）

- **詳細設定をページ3（メンバー登録後）に移動**: 「⚙️ 詳細設定（任意）」は、これまでページ1（バンド設定時点）にありましたが、この時点ではまだメンバーが登録されておらず、登録人数に応じた合理的なデフォルト値を計算できませんでした。メンバー登録後のページ3（プレビュー・出力ページ）に移動し、シフト生成前に確認・調整できるようにしました。
- **配置回数上限のおすすめ値を自動計算・自動入力**: ページ3を表示するたびに `/api/estimate-limits` を呼び出し、登録済みのバンド数・メンバースキル構成から算出したおすすめ値を「個人の卓/ステージ/合計配置回数上限」欄に自動入力するようにしました（未入力時のみ。一度でも手動で変更した項目は上書きしません）。あわせて、卓/ステージそれぞれのリーダー・アシスタント1人あたりの目安回数を欄の下に表示します。

## 主な改善点（v9）

### バックエンド（app.py）

- **配置回数の上限を「総量」から「進行度に応じたペース」に変更**: これまでの `shift_limit`（全バンド数×4÷メンバー数から算出する目安上限）は、イベント全体を通じた**総量**にしか達していないかを見ておらず、スキル3未満のアシスタントの絶対人数が少ないと、序盤のうちに必要枠を独占的に埋め続けてしまい、結果的に「特定の初心者が前半のバンドばかりに集中し、中盤・後半にはほとんど出てこない」という偏りが起きていました。今回、`shift_limit` を「今何バンド目まで進んだか（`band_index / total_bands`）」に対する目安ペースとして扱う方式（`_pace_overage`）に変更しました。ペースより前倒しで働きすぎているメンバーは優先度が下がり（`PACE_SOFT_OVERAGE` / `PACE_OVERAGE_PENALTY_WEIGHT`）、そのロールでリーダーになれないスキルのメンバー（アシスタント）はペースを大幅に超えると一時的に候補からハード除外され、強制的に休みを挟んでから中盤・後半に出番が持ち越されるようになります（`PACE_HARD_OVERAGE`）。複数日イベントでも日をまたいだ通し番号でペースを判定するため、特定の1日だけに特定のメンバーが集中する偏りも同様に抑制されます。
- **リーダーはハード除外の対象外**: 卓・ステージとも「スキル3以上のリーダーを最低1名含むこと」が必須のハード制約であるため、ペース超過によるハード除外はリーダーになれないスキルのメンバーにのみ適用し、リーダー候補には優先度を下げるだけに留めています。これにより、ペース管理を導入したことでバンドが不成立（リーダー不在エラー）になりやすくなることはありません。

## 主な改善点（v8）

### バックエンド（app.py）

- **連続勤務中の役割ジグザグを抑制**: 直前のバンドで連続して働いていたメンバーが、そのバンドと異なる役割（卓⇔ステージ）に切り替わろうとする場合、優先度を下げるようにしました（`ROLE_SWITCH_PENALTY`）。これにより「卓→ステージ→卓→ステージ」のようにバンドごとに役割が入れ替わるのを避け、連続勤務中はできるだけ同じ役割にまとまるようになります。あくまで優先度調整（ソフト制約）なので、他に候補がいない場合はやむを得ず切り替わることもあります。既存の役割継続ボーナス（`ROLE_CONTINUITY_BONUS`）は「同じ役割ならボーナス」でしたが、今回の変更は「異なる役割には明示的にペナルティ」を課すことで、この効果をより強めています。

## 主な改善点（v7）

### バックエンド（app.py）

- **卓・ステージの役割バランスをスコアに反映**: v6までは「一方の役割に偏っても調整しない」方針でしたが、卓・ステージそれぞれの優先度計算に、もう一方の役割の累計配置回数との差を反映するようにしました（`ROLE_BALANCE_WEIGHT`）。ステージ経験が多く卓経験が少ないメンバーは卓の優先度が上がり、卓ばかりのメンバーは卓の優先度が下がります（ステージ側も同様に逆方向で働きます）。ハード制約ではないため完全に均等になるとは限りませんが、「卓ばかり／ステージばかり」といった極端な型よりは緩和されます。連続配置に関する既存のロジック（`CONSECUTIVE_ROLE_LIMIT` / `ROLE_CONTINUITY_BONUS`）とは独立して働き、両方を合わせて「まとまりつつも最終的には両役割を経験する」形に寄せます。

## 主な改善点（v6）

### バックエンド（app.py）

- **同一役割への連続配置を3回までに制限**: 卓・ステージのどちらか一方に4回以上連続で配置され続けることがないよう、すでに3回連続で同じ役割に入っているメンバーは、その役割への優先度を大きく下げるようにしました（`CONSECUTIVE_ROLE_LIMIT` / `CONSECUTIVE_ROLE_PENALTY`）。`shift_limit` と同様に候補からの除外はせず、「他に候補がいない場合の最終手段」としてのみ許容します。
- **できれば2回以上まとまるように後押し**: 1バンドごとに卓⇔ステージが頻繁に入れ替わってしまうのを避けるため、連続上限（3回）にまだ達していない範囲では、同じ役割を継続する優先度を少し上げるようにしました（`ROLE_CONTINUITY_BONUS`）。
- **卓・ステージどちらかが0回のままでもOKという方針に**: 一方の役割ばかりに偏っても（例: 卓4回・ステージ0回）、それ自体は問題として扱わず調整を入れません。連続配置数の抑制のみを行い、役割の偏り自体は許容します。

### v5までの改善点

- **卓は「リーダー1名＋アシスタント1名」を基本形に**: 卓チームの残り枠は、スキル3以上のリーダーをもう1人追加するのではなく、スキル3未満のアシスタントを優先して補充するようにしました。アシスタント候補が誰もいない場合は、無理に埋めずリーダー1名のみのチームも成立として許容します（リーダーの重複配置を避けます）。ステージチームは従来通り、リーダー確保後は人数上限までスキルを問わず優先度順に補充します。
- **配置回数上限（shift_limit）を「予備要員化」**: これまでは1人あたりの配置回数の目安上限（`shift_limit`）に達したメンバーを候補から完全に除外していましたが、除外はせず優先度を大きく下げるだけにしました。普段は上限内のメンバーが優先されますが、他に候補がいない場合は上限を超えたメンバーも予備要員として配置できるため、無用な成立不可（エラー）が減ります。

### v4までの改善点

- **成立条件をロールベースに刷新**: 卓・ステージのスコア合計による閾値判定（`desk_score_threshold` 等）を廃止し、「スキル3以上のリーダーを最低1名含むこと」を必須のハード制約とする方式に変更しました。スキルは「3＝リーダー」「1＝アシスタント」の2段階運用が前提です。リーダーを1人も確保できないバンドは、アシスタントが何人いても成立不可（エラー）として弾かれます。
- **人数上限は「リーダー確保後の補充枠」に**: `desk_max_members` / `stage_max_members` は、リーダーを確保した上で何人まで補充するかを表す人数上限になりました。未設定時はデフォルトで2人（リーダー1名＋アシスタント1名）まで補充します。
- **成立しない場合はエラーで返却**: リーダーを確保できなかった場合、`error` と `reason`（不足の原因）付きで400エラーを返します。曖昧な「成立したことになっている」状態を防ぎます。あわせて、成立しなかったバンドを含む部分的な `shift` / `timetable` もレスポンスに含めて返すので、どこまで組めたかを確認できます。

### v3までの改善点

- **複数日NG時間のバグ修正**: 2日目以降もNG時間（日別指定）が正しく効くようになりました。
- **部分一致でのNG時間判定**: 時間帯が完全一致しなくても、1分でも重なっていればNGとして扱われます。
- **複数パターンから最良案を選択**: 貪欲法の弱点（前半で良い人を使い切る等）を緩和するため、優先度にランダムな揺らぎを加えた複数パターンを生成し、「成立バンド数」→「バンドごとの人数の均一性」→「配置回数の公平性」の順で最も良い案を採用します。
- **入力バリデーションの緩和**: `ng_bands` / `ng_times` / `req_bands` / `grade` はすべて省略可能になりました。欠けていても 500 エラーにはなりません。
- **個人・学年ごとの配置回数上限**: 連続性ボーナスによる偏りを抑えるため、個人単位・学年単位で卓/ステージへの合計配置回数に上限をかけられるようになりました（詳細は下記「シフト生成の詳細設定」を参照）。
- **連続生成時のカウントリセット漏れを修正**: 「シフトを生成」ボタンを連続で押すと、前回の生成結果（加算済みの `count`）がそのまま次回のリクエストに使われて配置回数の上限にすぐ抵触し、成立しなくなる不具合がありました。生成のたびに `count` / `desk_count` / `stage_count` を必ず0にリセットするよう修正済みです。

### フロントエンド（templates/index.html）

- **詳細設定UIを追加**: ページ1に「⚙️ 詳細設定（任意）」を追加し、卓/ステージの人数上限・個人/学年別の配置回数上限・生成パターン数を画面から設定できるようになりました。
- **メンバーに学年を設定可能**: メンバー登録フォームに「🎓 学年」欄を追加。学年別の配置回数上限（`grade_limits`）と連動します。
- **メンバーの編集機能**: 登録済みメンバーの「✏️ 編集」ボタンから内容をフォームに読み込んで上書き更新できるようになりました。修正のたびに削除→再登録する必要がありません。
- **成立しなかった場合もプレビューを表示**: シフトが一部成立しなくても、エラーで止めずに埋まった範囲をそのままプレビュー表示します。成立しなかったバンドは日タブとテーブルの該当セルに ⚠️ マークと不足内容（例: `リーダー（スキル3以上）不在`）を直接表示するので、どこが足りないか一目で分かります。

```
┌──────────────────────────────────────┐
│     フロントエンド (HTML/JS)          │
│   フロントエンド.html                │
└─────────────┬──────────────────────────┘
              │ HTTP (JSON)
              ↓
┌──────────────────────────────────────┐
│     バックエンド (Python/Flask)       │
│         app.py                       │
├──────────────────────────────────────┤
│  - generate_timetable()              │
```

**特徴**:
- **Python を軸**: `app.py` (Flask サーバー) が中核
- **自動反映**: Python に変更があれば HTML に自動的に反映
- **API ベース**: HTML は REST API で Python と通信

## 📖 使い方

### ステップ 1️⃣ : タイムテーブル設定

1. **開始時間**: イベント開始時間を設定 (例: 11:30)
2. **リハーサル時間**: リハの長さ（分）(例: 15分)
3. **本番時間**: 本番の長さ（分）(例: 10分)
4. **昼休憩**: 休憩の長さ（分）と、どのバンド後に挿入するか設定
5. **バンド追加**: 出演バンドを順番に追加

### ステップ 2️⃣ : メンバー条件設定

各メンバーについて以下を設定：
- **名前**: メンバーの名前
- **学年**（任意）: 学年ごとの配置回数上限（`grade_limits`）を使う場合に設定
- **卓スキル** (1-5): ミキサー・卓業務のスキル。**3以上＝リーダー、それ未満＝アシスタント**として扱われます（3＝リーダー、1＝アシスタントの2段階運用を推奨）
- **ステージスキル** (1-5): ステージ機材のスキル。卓スキルと同様に3以上がリーダー扱いです
- **出演バンド**: 出演するため、シフトに入れないバンド (選択式)
- **NG 時間帯**: 入れない時間帯 (日別、時・分をダイヤル式に選択、複数追加可)
- **希望バンド**: 優先的に割り当てたいバンド (選択式)

卓・ステージの各チームは「スキル3以上のリーダーを最低1名含むこと」が成立の必須条件です。リーダーになれるメンバーが1人も確保できないバンドは、アシスタント（スキル1〜2）が何人いても成立不可（エラー）として扱われます。卓チームはリーダー1名に加えてアシスタント1名を優先的に補充する運用が基本で、アシスタント候補がいなければリーダー1名のみでも成立とみなします。

登録済みのメンバーは一覧の「✏️ 編集」ボタンから内容を修正できます（削除して登録し直す必要はありません）。

### ステップ 3️⃣ : シフト生成・出力

1. **「シフトを生成」ボタン**: Python API にリクエスト送信
2. **結果確認**: タイムテーブルと割り当てを確認。もし一部のバンドで卓/ステージにリーダー（スキル3以上）を確保できなかった場合も、生成は止まらず埋まった範囲をそのままプレビュー表示します。該当バンドには ⚠️ マークと不足内容が表示されるので、原因を見ながら人数やスキル設定を調整してください。
3. **「エクセルで出力」**: シフト結果をエクセルファイルでダウンロード

### 🎛️ シフト生成の詳細設定（任意項目）

`/api/generate-shift` と `/api/generate-shift-multi-day` のリクエストボディに、以下のキーを追加すると挙動をカスタマイズできます。省略した場合は今まで通りの動作になります。

卓・ステージの成立条件はスコアではなく、「スキル3以上のリーダーを最低1名含むこと」（ロールベースのハード制約）です。`desk_max_members` / `stage_max_members` は、そのリーダーを確保した上で何人まで補充するかを表す人数上限です。卓は残り枠をアシスタント（スキル3未満）優先で補充し、アシスタントがいなければリーダー1名のみで成立とみなします。ステージは人数上限までスキルを問わず優先度順に補充します。

| キー | 説明 | デフォルト |
|---|---|---|
| `desk_max_members` | リーダー確保後、1バンドあたり卓に入れる人数の上限（リーダー含む。残り枠はアシスタント優先） | `2` |
| `stage_max_members` | リーダー確保後、1バンドあたりステージに入れる人数の上限（リーダー含む） | `2` |
| `desk_limit_per_member` | 1人が全日程を通じて卓に入れる回数の上限 | 無制限 |
| `stage_limit_per_member` | 1人が全日程を通じてステージに入れる回数の上限 | 無制限 |
| `total_limit_per_member` | 1人が全日程を通じて卓+ステージ合計で入れる回数の上限 | 無制限 |
| `grade_limits` | 学年ごとの合計配置回数の上限（下記参照） | なし |
| `candidate_count` | 内部で試すパターン数（多いほど良い組み合わせを探すが遅くなる、最大50） | `12` |

### 🔁 配置回数の上限とペース管理

1人あたりの配置回数の目安上限は、「イベント全体を通した進行度（今何バンド目まで進んだか）」に対するペース目標として使われます（v9〜）。今の進行度に対してペースより前倒しで働きすぎているメンバーは優先度が下がり、そのロールでリーダーになれないスキルのメンバー（アシスタント）はペースを大幅に超えると一時的に候補から除外され、強制的に休みが入ります。これにより、アシスタント候補の人数が少なくても、特定のメンバーだけが序盤のバンドに集中し続けることを防ぎ、中盤・後半にも自然と出番が持ち越されるようになります。

**ペースの基準値（v10〜）**: 基準値は次の優先順位で決まります。

1. そのロール専用の明示的な上限（`desk_limit_per_member` / `stage_limit_per_member`）
2. 卓+ステージ合計の明示的な上限（`total_limit_per_member`）
3. 登録済みのバンド数・メンバースキル構成（卓/ステージ × リーダー/アシスタントそれぞれの実際の人数）から自動推定した目安（`/api/estimate-limits` と同じロジック）

自動推定の基準値は、全メンバー数で一律に割るのではなく、そのロールでリーダーになれる人・なれない人（アシスタント）それぞれの**実際の人数**をもとに算出します。アシスタント適格者が少数しかいない場合でも、その少人数向けに正しく高めの目安回数が設定されるため、「まだ全体では上限に達していない」という誤判定による序盤への偏りを防げます。

前倒しの許容幅（ソフト超過・ハード除外のしきい値）は、基準値に対する**割合**で決まります（`PACE_SOFT_OVERAGE_RATIO` / `PACE_HARD_OVERAGE_RATIO`）。`desk_limit_per_member` などで小さい上限を明示指定した場合でも、その上限に向けて進行度に応じて配分されるため、少ない上限回数を前半だけで使い切ってしまうことを防ぎます。基準値が自動推定（ユーザー未設定）の場合、ハード除外はリーダーになれないスキルのメンバー（アシスタント）にのみ適用されます。卓・ステージとも「スキル3以上のリーダーを最低1名含むこと」が必須のハード制約であるため、リーダーになれるスキルのメンバーには優先度を下げるだけに留め、無用な成立不可（エラー）を防ぎます。一方、基準値がユーザーの明示的な上限設定に基づく場合は、リーダー・アシスタントの区別なくハード除外を適用します（ユーザー自身が意図して設定した上限のため）。

他に候補がいない場合は、ペースを超えたメンバーも「予備要員」として配置されます。複数日イベントでは日をまたいだ通し番号でペースを判定するため、特定の1日だけに配置が集中する偏りも同様に抑制されます。

### 🔍 配置回数上限の目安を確認する（/api/estimate-limits）

登録済みのバンド・メンバー構成から、配置回数上限のおすすめのデフォルト値を計算する軽量エンドポイントです。シフトは生成しません。フロントエンドではページ3（プレビュー・出力ページ）を開くたびに自動で呼び出され、詳細設定の上限欄に反映されます。

- `suggested_desk_limit_per_member` / `suggested_stage_limit_per_member`: 卓・ステージそれぞれのリーダー1人あたり目安回数（`leader_avg`）をそのまま切り上げた値。
- `suggested_total_limit_per_member`: 卓・ステージの `leader_avg` を単純合計した値に `TOTAL_LIMIT_SUGGESTION_MARGIN`（既定 `1.5`）倍の余裕を持たせてから切り上げた値。単純合計ちょうど（倍率1.0）だと、NG条件などで一部の人に負担が偏った際にすぐ上限へ抵触し、「リーダー候補が不足している可能性があります」というエラーが起きやすいため、あえて平均より多めの値を提案しています。

**リクエスト例**（`bands` / `days` のどちらの形式でも受け付けます）:
```json
{
  "bands": ["band1", "band2"],
  "members": [
    {"name": "先輩A", "skill_desk": 3, "skill_stage": 3, "count": 0},
    {"name": "後輩B", "skill_desk": 1, "skill_stage": 1, "count": 0}
  ],
  "desk_max_members": 2,
  "stage_max_members": 2
}
```

**レスポンス例**:
```json
{
  "num_bands": 18,
  "desk": {"leader_count": 13, "assistant_count": 2, "leader_avg": 1.4, "assistant_avg": 9.0},
  "stage": {"leader_count": 13, "assistant_count": 2, "leader_avg": 1.4, "assistant_avg": 9.0},
  "suggested_desk_limit_per_member": 2,
  "suggested_stage_limit_per_member": 2,
  "suggested_total_limit_per_member": 5
}
```

`grade_limits` の例（メンバーには `"grade": "1"` のように学年を設定してください）:

```json
{
  "grade_limits": {
    "1": { "desk_max": 8, "stage_max": 6, "total_max": 12 },
    "2": { "desk_max": 12, "stage_max": 10 }
  }
}
```

これは「1年生は卓に合計8回、ステージに合計6回、卓+ステージ合計12回まで」というように、学年単位で合計配置回数の上限をかける機能です。`desk_max` / `stage_max` / `total_max` はいずれも組み合わせ自由（一部だけの指定も可能）です。

メンバー側は `grade` を追加できます（文字列・数値どちらでも可、省略可）:

```json
{
  "name": "後輩B",
  "grade": "1",
  "skill_desk": 2,
  "skill_stage": 2,
  "count": 0
}
```

`ng_bands` / `ng_times` / `req_bands` / `grade` はすべて省略可能です。省略した場合は「制約なし」として扱われます。

## 🔄 Python に変更を加えるには

### 例: 卓・ステージの人数上限を変更したい

わざわざコードを書き換えなくても、リクエストに `desk_max_members` / `stage_max_members` を指定すれば変更できます（詳細は「🎛️ シフト生成の詳細設定」を参照）。フロントエンドを使う場合はページ3の「⚙️ 詳細設定」から入力するだけでOKです。

コード側のデフォルト値そのものを変えたい場合は、`app.py` 冒頭の定数を編集してください：

```python
LEADER_SKILL_LEVEL = 3          # ← この値以上のスキルを「リーダー」とみなす
DEFAULT_DESK_MAX_MEMBERS = 2    # ← desk_max_members 未指定時のデフォルト人数上限
DEFAULT_STAGE_MAX_MEMBERS = 2   # ← stage_max_members 未指定時のデフォルト人数上限
CONSECUTIVE_ROLE_LIMIT = 3      # ← 同一役割（卓/ステージ）への連続配置を許容する上限回数
ROLE_CONTINUITY_BONUS = 15      # ← 連続上限に達するまで、同じ役割を継続させる優先度ボーナス
ROLE_BALANCE_WEIGHT = 8         # ← 卓/ステージの累計配置回数の差に応じた優先度補正の重み（大きいほど役割バランスを強く後押し）
ROLE_SWITCH_PENALTY = 25        # ← 連続勤務中に直前と異なる役割へ切り替わる優先度を下げる幅（大きいほど連続勤務中の役割固定を強く後押し）
PACE_SOFT_OVERAGE_RATIO = 0.05  # ← 基準値に対する割合で、ここまでの前倒しは許容する（超えるまではペナルティなし）
PACE_SOFT_OVERAGE_MIN = 0.2     # ← 割合換算の許容幅が小さくなりすぎないための下限（回数）
PACE_OVERAGE_PENALTY_WEIGHT = 300  # ← ペースのソフト超過1につき優先度から差し引く重み（大きいほど前倒しを強く抑制）
PACE_HARD_OVERAGE_RATIO = 0.1   # ← 基準値に対する割合で、これを超えて前倒しすると、そのロールからハード除外して休ませる
PACE_HARD_OVERAGE_MIN = 0.35    # ← 割合換算の許容幅が小さくなりすぎないための下限（回数）
TOTAL_LIMIT_SUGGESTION_MARGIN = 1.5  # ← /api/estimate-limits がおすすめする合計配置回数上限に持たせる余裕（倍率）
```

修正後、Python サーバーを再起動（Ctrl+C で終了後、`python app.py` で再起動）すれば、HTML も自動的に新しいロジックを使用します。
